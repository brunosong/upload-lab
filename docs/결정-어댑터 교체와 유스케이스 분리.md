# 결정: 어댑터 교체와 유스케이스 분리

> 관련 문서: [README](../README.md)

기능을 바꾸거나 늘릴 때 어댑터만 바꿀지, 유스케이스부터 새로 만들지를 정한 기록입니다. "스트리밍으로 받은 목록을 디스크 대신 바로 DB에 넣으려면 어떻게 하나"를 이야기하다 정했습니다.

이 글에서는 다음을 다룹니다.

1. 우리 선택
2. 왜
3. 예제 1: 어댑터만 바꾸는 경우
4. 예제 2: 유스케이스부터 새로 만드는 경우
5. 트레이드오프
6. 아직 안 정한 것

> [!info] 미리 알아둘 용어
> - 유스케이스(in 포트): 바깥(컨트롤러)이 이 기능에 시키는 일을 적은 인터페이스입니다.
> - out 포트: 서비스가 바깥(디스크, DB)에 시키는 일을 적은 인터페이스입니다.
> - 어댑터: 포트를 실제로 구현한 클래스입니다. 디스크에 쓰거나 Mongo에 넣는 코드가 여기 있습니다.

---

## 1. 우리 선택

기준은 **"어디에 하느냐"가 바뀌었는지, "무엇을 하느냐"가 바뀌었는지** 하나입니다.

| 바뀐 것 | 할 일 |
|---|---|
| 어디에 하느냐 (저장 위치, 기록 위치) | 어댑터만 교체합니다. 유스케이스와 서비스는 그대로 둡니다. |
| 무엇을 하느냐 (결과, 중간 처리) | 기능 패키지를 새로 만들고 유스케이스부터 새로 둡니다. |

---

## 2. 왜

유스케이스는 바깥에 하는 약속입니다. 약속이 같으면 구현 위치만 바꾸면 되고, 약속이 다르면 새 약속이 필요합니다.

약속이 다른데 어댑터만 바꿔서 억지로 맞추면 두 가지가 꼬입니다.

- 포트 이름과 실제 동작이 달라집니다. `FileStoragePort`인데 파일을 저장하지 않는 식입니다.
- 줄 해석, 깨진 줄 거르기 같은 업무 규칙이 어댑터 안에 숨습니다. 어댑터는 어디에 어떻게 넣을지만 알아야 합니다.

이 lab은 "기능 하나에 패키지 하나, 중복 허용" 규칙이라, 유스케이스를 새로 만들 때는 컨트롤러가 비슷해도 복사해서 새 패키지에 둡니다.

---

## 3. 예제 1: 어댑터만 바꾸는 경우

업로드 기록을 메모리 대신 다른 곳에 남기는 경우입니다. 약속(`UploadRecordPort`의 `save`, `findAll`)은 그대로이고 위치만 바뀝니다.

lab에는 실제로 어댑터를 하나 더 넣어 두었습니다. MongoDB 없이 돌려 볼 수 있게 파일에 남기는 어댑터입니다.

```
streaming/adapter/out/record/
├── InMemoryUploadRecordAdapter.java   메모리. 서버를 끄면 사라짐
└── FileUploadRecordAdapter.java       uploads/records.jsonl 에 한 줄씩. 껐다 켜도 남음
```

### 어댑터 추가

같은 포트를 구현하는 클래스를 하나 만듭니다. 서비스, 유스케이스, 컨트롤러는 건드리지 않습니다.

```java
@Component
@ConditionalOnProperty(name = "lab.record.type", havingValue = "file")
public class FileUploadRecordAdapter implements UploadRecordPort {

    public synchronized void save(UploadedFile file) {
        // UploadedFile 을 JSON 한 줄로 바꿔 records.jsonl 끝에 붙임
    }

    public synchronized List<UploadedFile> findAll() {
        // records.jsonl 을 한 줄씩 읽어 UploadedFile 로 되돌림
    }
}
```

기존 메모리 어댑터에는 조건만 붙였습니다.

```java
@Component
@ConditionalOnProperty(name = "lab.record.type", havingValue = "memory", matchIfMissing = true)
public class InMemoryUploadRecordAdapter implements UploadRecordPort { ... }
```

### 교체

`application.properties`의 값 하나로 고릅니다. 바꾸고 재시작하면 어댑터가 바뀝니다.

```properties
lab.record.type=memory   # 또는 file
```

```
lab.record.type=memory  →  InMemoryUploadRecordAdapter 만 빈으로 올라감
lab.record.type=file    →  FileUploadRecordAdapter 만 빈으로 올라감
                              │
StreamUploadService(UploadRecordPort records)  ← 스프링이 올라간 쪽 하나를 넣어 줌
```

`@ConditionalOnProperty`는 조건이 맞을 때만 그 클래스를 빈으로 등록합니다. 둘 중 하나만 올라가니 `UploadRecordPort`를 구현한 빈이 항상 하나이고, 서비스 생성자에 그게 들어갑니다. 어느 쪽이 올라갔는지는 시작 로그에 `업로드 기록 어댑터: 메모리` 또는 `업로드 기록 어댑터: 파일`로 찍힙니다.

조건을 안 붙이고 두 클래스를 다 `@Component`로 두면, 같은 포트 구현이 둘이라 스프링이 무엇을 넣을지 몰라 시작할 때 오류가 납니다.

### 사용

서비스 입장에서는 달라지는 게 없습니다. 쓰는 쪽 코드는 그대로입니다.

```java
records.save(file);          // 메모리면 리스트에, 파일이면 records.jsonl 에
return records.findAll();
```

테스트에서는 스프링 없이 손으로 끼워 넣을 수도 있습니다. 서비스 생성자에 넣는 객체만 바꿉니다.

```java
new StreamUploadService(storage, new InMemoryUploadRecordAdapter());
new StreamUploadService(storage, new FileUploadRecordAdapter(dir, objectMapper));
```

`RecordAdapterSwapTest`에 두 방법이 다 있습니다. 손으로 끼운 파일 어댑터는 새로 만들어도 기록이 남고, 메모리 어댑터는 사라지는 것을 확인합니다. 설정값을 `memory`, `file`로 바꿨을 때 실제로 끼워지는 어댑터가 바뀌는 것도 확인합니다.

2026-10-14에 앱으로도 확인했습니다. `file`로 띄워 하나 올리고 재시작하면 목록에 1건이 남았고, `memory`로 재시작하면 0건이었습니다.

### 교체하는 다른 방법

| 방법 | 쓰는 법 | 맞는 경우 |
|---|---|---|
| `@ConditionalOnProperty` (lab에서 씀) | 설정값으로 고름 | 같은 환경에서 구현을 골라 보고 싶을 때 |
| `@Profile` | `@Profile("local")`, `@Profile("prod")` | 개발은 메모리, 운영은 Mongo처럼 환경별로 나눌 때 |
| 옛 어댑터 삭제 | 새 어댑터만 `@Component` | 완전히 갈아탈 때. 가장 단순 |
| `@Primary` | 새 어댑터에 붙임 | 잠깐 덮어쓸 때. 둘 다 올라가 있어 헷갈리기 쉬움 |

### MongoDB 어댑터도 같은 방식

Mongo로 옮길 때도 클래스 하나를 더 만들고 `havingValue = "mongo"`를 붙이면 됩니다.

```java
@Component
@ConditionalOnProperty(name = "lab.record.type", havingValue = "mongo")
public class MongoUploadRecordAdapter implements UploadRecordPort {

    private final MongoTemplate mongo;

    public MongoUploadRecordAdapter(MongoTemplate mongo) {
        this.mongo = mongo;
    }

    @Override
    public void save(UploadedFile file) {
        mongo.insert(file, "uploads");
    }

    @Override
    public List<UploadedFile> findAll() {
        return mongo.findAll(UploadedFile.class, "uploads");
    }
}
```

`StreamUploadService`, `StreamUploadUseCase`, 컨트롤러는 한 줄도 안 바뀝니다. Mongo 어댑터는 lab에 Mongo 의존성이 없어서 아직 넣지 않았습니다.

## 4. 예제 2: 유스케이스부터 새로 만드는 경우

스트리밍으로 받은 목록 파일을 디스크에 쓰지 않고 한 줄씩 읽어 바로 DB에 넣는 경우입니다. 입력은 같은 `InputStream`이지만 약속이 다릅니다.

```java
// streaming: 받은 걸 파일로 저장하고 크기와 해시를 알려 준다
UploadedFile upload(String originalName, InputStream body);

// directingest: 받은 걸 한 줄씩 읽어 DB에 넣고 몇 줄 넣었는지 알려 준다
IngestResult ingest(InputStream body);
```

그래서 새 패키지를 만듭니다.

```
com.example.uploadlab
├── streaming/                        그대로 둠
└── directingest/                     새로 만듦
    ├── domain/ListRow.java, IngestResult.java
    ├── application/port/in/StreamIngestUseCase.java
    ├── application/port/out/ListRowWriterPort.java
    ├── application/StreamIngestService.java       한 줄씩 읽고 5000줄씩 묶어 포트로 넘김
    └── adapter/
        ├── in/web/StreamIngestController.java      streaming 것과 거의 같아도 복사
        └── out/mongo/MongoListRowWriterAdapter.java
```

두 기능을 나란히 놓으면 이렇게 다릅니다.

| | streaming | directingest |
|---|---|---|
| 컨트롤러 | `request.getInputStream()`을 넘김 | 똑같음 |
| 서비스 | 스트림을 통째로 저장 포트에 넘김 | 한 줄씩 해석해서 묶음으로 넘김 |
| out 포트 | `FileStoragePort.save(InputStream)` | `ListRowWriterPort.saveAll(List<ListRow>)` |
| 받을 수 있는 파일 | 아무 파일 | TSV 텍스트만 |

하지 않기로 한 방법도 남겨 둡니다. `FileStoragePort`를 구현한 Mongo 어댑터 안에서 줄을 읽어 넣으면 서비스를 안 고쳐도 돌아는 갑니다. 하지만 2번에서 말한 두 가지가 꼬여서 쓰지 않습니다.

## 5. 트레이드오프

- 기능이 늘 때마다 컨트롤러, 포트처럼 비슷한 코드가 패키지마다 생깁니다. 이 lab은 한 폴더만 보면 기능이 다 보이는 쪽을 택해서 중복을 받아들입니다.
- 실무 프로젝트라면 공통 부분을 묶거나, 한 유스케이스에 메서드를 늘리는 쪽을 고를 수도 있습니다.

---

## 6. 아직 안 정한 것

- `directingest` 기능을 실제로 만들지는 정하지 않았습니다. 만든다면 `spring-boot-starter-data-mongodb`와 MongoDB용 `docker-compose.yml`이 필요합니다.
- 운영에 가까운 프로젝트라면 `@ConditionalOnProperty` 대신 `@Profile`로 환경별로 나눌지 정하지 않았습니다. lab은 같은 환경에서 바꿔 보는 게 목적이라 설정값으로 고릅니다.

---

## 정리

- 어디에 하느냐만 바뀌면 어댑터만 교체합니다. 예: 업로드 기록을 메모리에서 파일이나 Mongo로.
- 교체는 같은 포트를 구현한 클래스를 추가하고 `@ConditionalOnProperty`로 하나만 올라가게 해서, `lab.record.type` 값으로 고릅니다.
- 무엇을 하느냐가 바뀌면 유스케이스부터 새로 만듭니다. 예: 파일 저장 대신 줄 단위 DB 적재.
- 약속이 다른데 어댑터로 억지로 맞추면 포트 이름이 거짓말이 되고 업무 규칙이 어댑터에 숨습니다.
- 이 lab은 새 유스케이스를 새 기능 패키지에 두고, 비슷한 코드의 중복을 받아들입니다.
